# Web 交互惯例

先用一句话说清用户正在做的事，以及操作后最可能继续做的事。例如“连续检查画面，点一次标记后还要按方向键看下一帧”。同一个按钮放在工具栏、表单和弹窗里，合理的下一步可能不同。

## 设计新页面或重做流程

整页设计沿用主设计流程已确定的用户任务、信息层级和布局。如果同时使用 impeccable，由它组织页面方案；把下面的表放进同一份方案。先讲清关键操作，再用效果图表达。用户只要交互建议时，直接回答对应场景。

先用一两句话交代页面区域、各区展示哪些内容、用户从哪里开始。列出涉及决策的组件，相同职责的重复项合并一行。优先考虑项目现有组件；遇到容易混用的控件，按意图查[组件选型](references/component-choice.md)。

| 区域与组件 | 负责什么 | 触发 → 结果和后续操作 | 桌面 / 手机 |
|---|---|---|---|
| 订单列表 → 详情 | 核对某笔订单，随后继续比较其他订单 | 选择一行后展示该单；返回列表时能找到原来那一行 | 桌面需要连续比对时用并排的非模态侧栏；窄屏详情较长时进入详情页，返回恢复筛选和位置 |
| 归档反馈 | 确认刚才的操作，提供恢复机会 | 归档后列表更新，短暂提供撤销；错过后仍能从归档区恢复 | 两端共用同一行为 |

用当前任务的真实内容替换示例。对关键流程补一个容易出错的验收情境，例如“提交失败后能否就地重试”。用一两句话即可说明的小改动，直接用文字。用户明确只做桌面或手机时按指定端设计；覆盖两端时，结合可用空间、输入方式、是否需要同时看两处内容和返回路径说明差异，允许两端完全共用。

## 评审或实现已有交互

1. 沿实际入口走一遍。记录**输入方式 → 动作 → 可见结果 → 下一步**。区分焦点、焦点环、选中态和文本选区。用户说“被选中”时，先确认是样式问题，还是下一次按键真的送错了地方。
2. 只读命中场景的参考。焦点、快捷键、表单控件、浮层读[控件与输入](references/controls.md)。分页、列表选择、加载、提交、撤销和错误恢复读[连续操作与反馈](references/flows.md)。
3. 选最接近的原生控件或现有组件。先检查它已经提供的键盘、触摸、读屏和恢复行为，再决定要接管哪一项。对自定义行为说清理由和退出路径。
4. 用下一次真实操作验收。交互缺陷优先在浏览器里连续做两步。单测适合覆盖状态和边界；合成 click、静态截图或 DOM 中多了一个属性，都不能证明键盘焦点、默认提交、触屏和读屏体验正常。报告实际验证的方式。

设计时给出所选行为和一个验收例，不必为小改动出长文档。评审时写出触发动作、实际结果、期望的下一步和影响。限定在用户请求的页面和流程内。

## 如何取舍

- **标准要求**看具体成功准则及其适用条件。例如键盘可操作、焦点顺序合理、键盘焦点可见。查具体条款后再作合规判断。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **控件惯例**看对应模式。ARIA APG 是实现指导；Adobe、微软等设计系统提供可参考的做法。一家产品的字号、分页形态或按钮顺序不能直接当作全行业规定。[WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/) · [Microsoft Fluent 2](https://fluent2.microsoft.design/accessibility)
- **场景选择**由任务决定。分页箭头适合反复触发；编辑器工具执行后，下一次输入往往属于内容区。对有合理分歧的地方，按用户已明确的习惯、本项目已有约定和实际使用验证取舍。
