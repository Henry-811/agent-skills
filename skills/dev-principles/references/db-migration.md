## 数据库迁移与 Schema 演进

当变更涉及表、字段、索引、约束、枚举值、数据回填、历史数据修复或读写路径兼容时，必须使用本 reference。

核心原则：**兼容不是默认，先执行 R8。**先验证静态读写者、发布/生产数据、部署拓扑和回滚依赖。证据未知时先补证据，不能先堆双读/双写；证据确认无影响时可以直接删除旧结构。确认有影响时根据部署策略选择：存在滚动部署、独立消费者或零停机要求时使用 expand / migrate / contract；能够在维护窗口内协调全部读写者时，可采用带 preflight、备份/回滚、原子切换和事后验证的受控迁移。兼容阶段是有退出计划的迁移手段，不是最终架构。

在修改 migration 前必须确认它是否已提交/共享，或已进入任何非一次性环境的 migration ledger。满足任一条件的 revision 都视为 immutable，修正必须新增 forward revision；“直接删除”指通过当前新 revision 删除旧结构，不是改写历史。只有可证明尚未提交、未共享且仅用于可丢弃本地数据库的 migration 才能原地调整，调整后必须从 baseline 重跑相应迁移验证。

### 触发条件

- 新增、删除、重命名表或字段。
- 修改字段类型、默认值、nullable、唯一约束、外键、索引。
- 新增状态枚举、软删除字段、归档字段、租户字段、权限字段。
- 需要 backfill、数据清洗、历史数据修复或批量重算派生字段。
- 新旧版本服务可能同时运行，或部署/回滚期间读写路径会跨版本。

### 强制检查

| 检查项 | 要求 |
|---|---|
| 影响证据 | grep 静态读写者；确认发布/ledger 状态；经授权后以最小权限查询必要的生产聚合或计数，禁止导出无关敏感 payload；确认原子切换或混部窗口与回滚依赖。证据不足时先补证据或升级风险决策 |
| 演进策略 | 无影响直接删除；能协调全部消费者时可受控维护窗口切换；存在滚动部署、独立消费者或零停机要求时才要求兼容矩阵 |
| Expand | 仅在选择兼容策略时先做向后兼容的新增：新表/新字段/新索引/宽松约束；避免一步删除或改语义 |
| Write Path | 新代码写入哪些字段；是否需要双写；写失败时如何处理 |
| Read Path | 新代码从哪里读；是否需要双读或 fallback；默认值和 NULL 语义是否明确 |
| Backfill | 数据量、批大小、幂等性、可暂停/恢复、锁表风险、失败重试和进度记录 |
| Contract | 明确 owner、可验证的退出条件/信号、最晚移除版本或日期和删除任务；移除前确认无读写者 |
| Rollback | 先区分应用回滚、数据库 downgrade、备份恢复和 forward-fix。只有明确承诺可执行 downgrade 时，才要求它安全处理已写入的新数据；破坏性或不可逆变更不得伪造“形式可逆”，应声明不可逆检查点并验证备份恢复或 forward-fix |
| Integrity | 唯一性、外键、状态迁移、派生数据一致性如何验证 |
| Performance | 索引创建、锁、长事务、复制延迟、查询计划变化是否可控 |
| Observability | migration/backfill 进度、错误率、耗时、锁等待、受影响行数是否可观测 |

### Migration Plan 输出

涉及 schema 或数据迁移时，必须产出 Migration Plan：

1. **变更类型**：schema-only / schema + code / backfill / data repair / destructive cleanup。
2. **影响证据与演进决策**：记录 migration 发布/ledger 状态、静态读写者、经授权的必要生产证据、部署拓扑与回滚依赖；无影响时说明直接删除依据，能协调全部消费者时说明受控切换方案，只有存在混部或独立消费者时才产出兼容矩阵。证据未知时列出补证据动作或 risk owner 的明确决策，不能默认生成兼容层。
3. **发布阶段**：受控切换需列维护窗口、preflight、备份/回滚、原子切换和验证；兼容策略需列 expand、应用切换、backfill、contract，每阶段写明进入/退出条件，contract 还必须包含 owner、退出信号、最晚移除节点和删除任务。
4. **读写策略**：单写/双写、单读/双读、fallback、默认值、NULL 语义。
5. **Backfill 计划**：批处理方式、幂等键、进度记录、失败恢复、限速策略。
6. **回滚计划**：每个阶段如何回滚；哪些步骤不可逆；不可逆前需要什么确认。
7. **验证计划**：迁移前后行数、约束、一致性抽样、关键查询、生产默认路径测试。若承诺数据库 downgrade，必须覆盖 upgrade → downgrade → re-upgrade；若不承诺，则验证文档中声明的备份恢复或 forward-fix 路径，不为通过检查而保留旧运行时语义。
8. **监控与告警**：需要看的日志、指标、trace、告警阈值和 owner。

**门槛检查**：如果某个 schema 变更无法回答“部署中途回滚会怎样”或“旧读写者是否仍存在”，不得进入实现；先补证据并由 owner 选择受控切换或兼容发布，不能机械拆成兼容阶段。
