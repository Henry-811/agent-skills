## 跨层变更验证与不变量台账

本 reference 约束中大型改动的端到端可追溯性，以及大批量跨层修改完成后的最终独立复审。它补充逐模块设计、测试和 diff review，不能被这些局部检查替代。

### 触发条件

- **MUST** 中等或大型改动建立并持续维护不变量台账；即使某项只涉及单层，也要在不适用列写明理由。
- **MUST** 大批量跨层修改在所有批次合并到最终工作树、相关测试通过后，执行一次独立全库复审。
- 小型 bugfix、UI 微调和纯配置变更默认不要求台账或全库复审；若它实际改变共享不变量、跨层契约或并发边界，则按中大型改动处理。

### 不变量台账

台账在方案设计时建立，在实现和修复过程中同步更新，最终内容必须指向当前代码而非计划中的文件。它可以放在 Feature Spec、Design Plan 或本次 review artifact 中；已有合适文档时不要为了形式再建一份重复文档。

| 字段 | 必须记录的内容 |
|---|---|
| 不变量 / 业务规则 | 稳定、可判定的规则；违反后具体会产生什么错误状态 |
| 权威数据源 | authoritative model/table/event/外部系统；谁写、谁读，派生值从哪里计算 |
| 锁 / 事务边界 | 聚合锁顺序、数据库事务、CAS/idempotency 边界；不需要锁时写明理由 |
| API 投影 | 请求/响应字段、错误语义、空值和版本边界；没有 API 时写明内部边界 |
| 前端状态 | authoritative server state、本地草稿/cache、coordinator/effect、失效与重同步路径；没有前端时写明理由 |
| 回归测试 | 具体测试文件和场景，覆盖正常、拒绝、竞态或恢复中的哪些风险 |

执行要求：

1. **MUST** 每条不变量横向贯通所有列；禁止每层各写一份互不对应的清单。
2. **MUST** 从权威数据源查全 readers/writers，不能只记录当前 diff 中出现的入口。
3. **MUST** 锁、事务、API 或前端状态发生变化时，同一变更内更新对应台账行和回归测试映射。
4. **MUST** Test Plan 以台账为输入；一条关键不变量没有验证方式时，变更不能标记完成。
5. **ANTI-PATTERN**：用“后端已处理”“前端已覆盖”“有单测”等泛化描述代替文件、边界和场景。

### 独立全库复审门禁

独立全库复审发生在逐批实现和 diff review 之后，检查的是最终系统，而不是各批次结论的汇总。

1. **独立性**：由未主导本次实现的 reviewer 或新鲜上下文完成；reviewer 必须从当前代码和原始规格重建判断，不能只复述实现者摘要或预期答案。无法获得独立 reviewer 时应明确报告门禁未满足，不能把自审标为独立复审。
2. **全库范围**：从应用入口、领域规则和台账出发扫描最终代码树，跨后端、数据库/migration、API schema、前端 coordinator/state、测试和设计文档核对所有相关 readers/writers。第三方依赖、生成物、构建产物可排除，但必须记录排除项和理由。
3. **不是只看 diff**：diff 用于定位变化，但 reviewer 必须读取未改动的消费者、异常处理、恢复路径和默认生产路径；逐批 review 全绿不能替代最终复审。
4. **证据要求**：每个 finding 指向当前文件/行号、违反的不变量或规则、影响和最小修复；没有实际证据不定级、不扣分。
5. **闭环**：修复复审 finding 后执行受影响测试；若修复再次跨层或改变台账，更新台账并对该风险面复审。P0/P1 未关闭时不得交付。

最终复审记录至少包含：reviewer 独立性、扫描范围、排除项、不变量台账核对结果、findings 与处置、最终验证命令及结果。

### 常见反模式

- 每个 commit 都做 diff review，但没有针对最终工作树的全库复审。
- reviewer 只读变更摘要或测试结果，没有读取真实调用链和未修改消费者。
- 台账在实现结束后为过检查临时补写，内容与实际代码、锁或 API 已漂移。
- 用一个高层 E2E 的“流程成功”代替每条关键不变量的边界、竞态和失败验证。
