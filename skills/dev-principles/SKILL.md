本 skill 是编码规范的权威入口。任何编写、修改、审查、重构代码或配置的任务，都必须先读本文件；再按风险面读取 `references/` 中的展开细则。

核心原则：**主文件是底线和路由，references 是命中风险面时必须加载的细则**。拆分只减少上下文噪声，不降低任何规则强度。

## 规则强度分级

- **MUST** — 必须遵守，违反通常产生明显风险或缺陷。
- **SHOULD** — 默认遵守；允许有理由的例外，但需说明理由。
- **MAY** — 推荐做法，视场景采用。
- **ANTI-PATTERN** — 明确反模式，应主动避免。

## 所有代码变更的硬底线

这些规则不因改动小而失效：

1. **错误不静默**：每个 `catch` / `except` 必须日志、抛出、转换为用户可见错误，或写明可忽略的业务理由。
2. **依赖方向单向**：源码依赖按项目分层保持无环；核心业务不依赖框架、数据库、UI，基础设施通过业务定义的接口接入。运行时调用方向不等于源码依赖方向。
3. **边界完整校验**：用户输入、API 参数、外部响应在系统边界校验；内部模块基于契约协作。
4. **配置与代码分离**：不硬编码 URL、密钥、环境差异和无解释魔法数字。
5. **模式一致但不盲从**：同类操作沿用项目内合理模式；发现坏模式时先指出，再选择最小安全修正。
6. **业务按域组织**：业务代码优先归属对应域；共享基础设施下沉，共享业务规则独立成域。
7. **改动必须验证**：验证方式按风险选择；bugfix、重构、业务规则、权限、并发、数据一致性不能只靠目测。
8. **API 是契约**：请求、响应、错误码、版本兼容和幂等语义必须明确，不能让调用方猜。
9. **关键路径可观测**：关键用户路径、跨系统边界、异步任务、失败分支必须能定位影响范围和原因。
10. **触发式检查优先执行**：命中 R1-R9 时必须执行对应 grep / lookup / signature 对照，不能凭直觉跳过。
11. **异步编排必须真实验证**：前端行为由 coordinator / effect / subscription / polling 驱动时，至少一条测试必须执行真实生产编排路径；不会执行 effect 的伪 Hook 不能证明异步行为正确。
12. **跨层不变量必须可追溯**：中大型改动维护业务规则到数据、事务、API、前端状态和回归测试的不变量台账；大批量跨层改动完成后必须对最终代码树进行独立全库复审。

## Reference Loading Rules

先读本文件，再按命中的风险面读取一个或多个 reference。一个任务可以同时加载多个 reference。

| 命中场景 | 必须读取 |
|---|---|
| 新模块、重构、跨层调用、Repository / Service、领域拆分、共享模块、依赖方向、入口脚本承载业务流程 | `references/architecture.md` |
| 应用代码、错误处理、状态副作用、认证安全、常量、API client、数据访问、缓存、重试、限流、配置 | `references/implementation.md` |
| 写测试、修 bug、重构、业务规则变化、验证行为、mock/fake/provider、E2E/集成/单元测试选择 | `references/testing.md` |
| 新增/修改 API、DTO/schema、错误码、外部服务调用、幂等、分页、关键路径、异步任务、失败分支、日志、指标、trace、告警 | `references/api-observability.md` |
| 数据库 schema 变更、migration、字段/索引/约束、backfill、数据修复、读写兼容、回滚 | `references/db-migration.md` |
| 中大型改动、不变量跨层传递、大批量跨层修改、需要最终独立全库复审 | `references/change-verification.md` |

### 产物深度与时机

实现前明确本次适用的契约、设计和验证方式；优先引用已有规格，只补变化部分。各 reference 的 Plan 是所需信息，不强制另建同名文档；可合并到一个 feature 文档或任务记录。不适用项写 `N/A + 理由`，无待确认项写“无”，不得为凑字段制造决策或问题。小 bugfix 可以用“复现条件 → 修复断言 → 验证命令”三项代替长表。纯评审输出证据与发现，不要求先生成整套实现文档。

## R1-R9 触发式强制检查摘要

命中下列代码形态时，必须读取 `references/trigger-checks.md` 并执行对应动作。这里保留摘要，避免最高价值规则被藏到细节文件里。

| # | 触发条件 | 必须动作 |
|---|---|---|
| **R1** | 新增 gate / filter / permission / source / stale / visibility / 任何过滤数据的判断 | 从字段或数据定义出发 grep 所有 readers / writers / service entrypoints，确认 gate 在数据流必经处。 |
| **R2** | 调 helper / service 有 ≥2 个同类型且语义不同的 positional args | 查 signature 并对照参数来源；可控接口用 keyword args / named options / wrapper type。固定第三方接口不能改签名时，保留具名局部变量与映射验证。 |
| **R3** | 新增 raise / 新异常类型 / 改异常语义 | grep 上游 `except` / middleware / global handler / `.catch`，确认不会被吞或错映射。 |
| **R4** | SQL / ORM predicate 涉及 nullable column 且用 `!=` / `<>` / `NOT IN` / `NOT LIKE` | 检查 NULL 三值逻辑；需要包含 NULL 时用 `IS DISTINCT FROM` 或显式 `OR col IS NULL`。 |
| **R5** | 用 fake / mock / local fallback / in-memory provider 验证受本次变更影响的 provider 或集成行为 | 至少一条 case 覆盖 production default provider / backend / branch / SQL path；使用隔离测试环境，不连接生产写入。纯逻辑单测不因此被强制升级为集成测试。 |
| **R6** | 新增字段 / 复用相似字段名 / 跨模块借用 model 属性 | 查 model / schema / migration / API contract、写入点和读取点，不能按名字猜。 |
| **R7** | 新增 boolean / timestamp / enum 状态字段 | 同一变更集定义写入、读取/gate、退出/恢复语义；有意不可逆的终态说明理由与后续行为，不强造恢复功能。纯 schema staging 必须保持 inert 并说明启用点。 |
| **R8** | 新增/保留跨版本兼容路径，或破坏性删除/重命名跨边界、跨部署或持久化契约（API、event/job payload、schema、外部配置等） | 先验证消费者、发布/生产使用、部署拓扑和回滚影响；证据未知先补证据，无影响直接删除，有影响则按部署约束选择受控切换或有界兼容。兼容必须有 owner、退出信号、最晚移除节点和删除任务。 |
| **R9** | 前端测试涉及 Hook/effect、异步 coordinator、subscription、polling、timer、请求竞态或服务端状态向本地状态收敛 | 至少一条测试运行真实生产 Hook/coordinator/effect，并在会执行和 flush effect 的环境中等待状态收敛；只 mock 网络、时钟等外部边界。把 `useEffect` 替换为 no-op、仅调用纯函数或伪造 Hook 返回值的测试不能作为异步行为证明。 |

## 执行流程

1. 明确任务规模和风险面。
2. 读取本文件和命中的 references。
3. 实现前先验证任务合理性：如果规则明确说不该做，先指出；不要机械执行错误任务。
4. 中大型改动在实现前建立 `references/change-verification.md` 定义的不变量台账，并随设计和实现持续更新；不适用的层必须写明理由，不能留空或默认跳过。
5. 进入实现：先基础后功能，Make it work → Make it right → Make it fast。
6. 验证时按 `references/testing.md` 与任务风险选择单元、集成、E2E 或手动验证。
7. 大批量跨层修改在全部批次完成、测试通过后，按 `references/change-verification.md` 对最终代码树执行一次独立全库复审；逐批 diff review 不能替代此门禁。
8. 交付前执行本文件自检；命中过 R1-R9 的任务需说明已执行对应检查。

## 自检清单

写完代码、审查或给出建议前，逐项确认：

- [ ] **references 已加载**：是否读取了本任务命中的 reference？若没有，是否说明了不命中的理由？
- [ ] **不混乱**：同一文件是否混了不同域的逻辑？
- [ ] **不过度**：拆分方式是否最简？有没有不必要的间接层、抽象？
- [ ] **域归域**：业务代码是否在对应域包内？共享服务是否独立？
- [ ] **不跳层**：数据操作是否通过适当抽象层？简单场景的例外是否受控？
- [ ] **不重复**：重复逻辑是否值得提取？是否只按表面相似硬抽象？
- [ ] **不静默**：catch / except 是否有显式处理或业务说明？
- [ ] **契约清晰**：API 请求、响应、错误码、版本兼容和幂等语义是否明确？
- [ ] **可观测**：关键路径是否有日志、指标或 trace，失败后能否定位影响范围和原因？
- [ ] **演进决策有证据**：涉及 API / schema / data 语义变更时，是否先确认发布与消费者、生产数据、部署拓扑和回滚影响？证据未知是否先补齐或显式升级风险决策；无影响是否直接清理；有影响时选择受控切换还是有退出计划的兼容，依据和验证是否明确？
- [ ] **不变量可追溯**：中大型改动是否维护了“业务规则 → 数据源 → 锁/事务边界 → API 投影 → 前端状态 → 回归测试”台账，并让每项能落到当前代码和测试？
- [ ] **最终全库复审**：大批量跨层修改是否由独立上下文基于最终代码树完成全库复审，而不是只累计逐批 diff review？范围、排除项和发现是否留痕？
- [ ] **触发式检查已执行**：命中 R1-R9 时，是否完成对应 grep / lookup / signature 对照？
- [ ] **测试路径真实**：测试是否至少覆盖需要验证的 production default path？
- [ ] **前端异步路径真实**：涉及 coordinator/effect 的测试是否真的执行并 flush 生产 effect、等待状态收敛，而不是使用不会执行 effect 的伪 Hook？
- [ ] **不盲从**：是否只是跟随已有模式而没有质疑其合理性？
- [ ] **有理有据**：若偏离 SHOULD，是否明确说明例外理由、边界和代价？
- [ ] **不脑补**：有没有执行本 skill 或 references 中不存在的规则？
