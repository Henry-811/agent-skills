在分析需求、设计功能、验证交付时，使用以下清单确保业务层面的完整性。

## 前置依赖

- **MUST** 本 skill 的输入是 concept-exploration 产出的 **Concept Brief**（或同等深度的需求定义：目标用户、核心问题、核心概念、MVP、非目标、关键假设已明确）。本 skill 校验 Brief 推导出的业务规则、流程、边界是否完整，**不重新定义问题**。
- **MUST** 若目标用户、核心概念或 MVP 等实质信息缺失，回退到 concept-exploration 补齐；仅仅没有名为 Concept Brief 的文档不构成缺口。既有规格和已确认需求包含等价信息时直接复用，不要求用户重复确认。
- **判断标准**：本 skill 的每一项检查（业务规则、用户流程、领域模型、边界）都假设"做什么"已经确定。如果发现某项需要先回答"我们到底要做什么"，那就是 concept 缺口，回退而不是猜测。

## 方法论背景

本清单综合了以下方法论的核心思想：

- **DDD（领域驱动设计）**：统一语言（代码与业务术语一致）、限界上下文（业务边界清晰）、领域事件（业务动作驱动后续流程）
- **BDD（行为驱动开发）**：用具体例子定义期望行为（Given-When-Then），既是需求也是验收标准
- **JTBD（Jobs to Be Done）**：关注"用户要完成什么任务"而非"用户要什么功能"——功能是手段，任务完成才是目的
- **Use Case Analysis**：主流程 + 替代流程 + 异常流程，确保每个用户操作都有明确后续

## 执行清单

### 1. 需求完整性

- [ ] 这个功能解决什么问题？为谁解决？
- [ ] 用户的具体使用场景是什么？（用例，不是抽象描述）
- [ ] 验收标准是什么？（怎样算"做完了"）
- [ ] 不做什么？（明确边界，防止范围蔓延）

### 2. 统一语言

- [ ] 代码命名（类、函数、变量、表字段）是否与业务术语一致？
- [ ] 文档、代码、讨论是否使用同一套术语？（消除歧义）

### 3. 业务规则完整性

- [ ] 业务规则是否全部识别并记录？
- [ ] 每条规则的约束条件是否明确？（何时触发、谁受影响）
- [ ] 规则之间是否有冲突或遗漏？
- [ ] 关键业务规则是否有对应的测试场景覆盖？（交叉验证 → dev-principles 场景覆盖清单）

### 4. 用户流程

- [ ] 主流程（Happy Path）是否完整？从触发到结束。
- [ ] 替代流程：用户可能走的其他合理路径？
- [ ] 异常流程：出错时用户看到什么？如何恢复？
- [ ] 流程中有没有断点、死路、不合理的跳转？

### 5. 领域模型

- [ ] 涉及哪些实体？它们之间的关系？
- [ ] 哪些实体必须一起变更、一起保持一致？（聚合边界）
- [ ] 对现有数据模型的影响：新增表？修改字段？迁移？
- [ ] 业务上"发生了什么"是否需要触发后续流程？（领域事件）

### 6. 边界情况

- [ ] 数据为空时怎么办？（首次使用、无历史数据）
- [ ] 权限边界：不同角色看到/能做什么？
- [ ] 并发场景：多人同时操作会怎样？
- [ ] 时间边界：过期、超时、时区？

### 7. 目标验证

- [ ] 这个功能是否真的解决了用户的核心任务？（不是堆功能）
- [ ] 最小可行方案是什么？（先解决核心问题，再迭代）
- [ ] 有没有更简单的方式达到同样的目的？

## 输出格式：Feature Spec / Acceptance Scenarios

需求/设计模式：产出或更新可交给 dev-principles 的 Feature Spec。可复用已有文档，只补变更部分；不适用项注明理由：

1. **Concept Brief 来源**：引用本次使用的 Brief 或等价需求定义；若缺失，停止并回退到 concept-exploration。
2. **统一语言**：列出核心业务术语、定义、同义词/禁用词，以及代码/API/文档命名建议。
3. **业务规则表**：每条规则包含触发条件、约束、允许/禁止的行为、用户可见结果、关联验收场景。
4. **用户流程**：主流程、替代流程、异常/恢复流程；每条流程从触发到最终结果闭环。
5. **领域模型影响**：实体、关系、聚合边界、数据模型变更、领域事件或后续流程。
6. **边界场景**：空值、权限、并发、时间、重复提交、外部依赖失败等需要验证的场景。
7. **Acceptance Scenarios**：用 Given-When-Then 写关键验收场景；每条关键业务规则至少对应一个场景。
8. **非目标确认**：明确当前不做什么，避免实现阶段扩范围。

**门槛检查**：如果 Feature Spec 无法明确推导出验收场景，不进入实现；如果验收场景无法映射到测试或验证方式，交给 dev-principles 的 testing reference 生成 Test Plan 后再实现；如果领域模型影响包含 schema 变更、数据迁移、backfill 或历史数据修复，必须交给 dev-principles 的 db-migration reference 生成 Migration Plan 后再实现。

交付验证模式：以已确认的规格为基线，逐条输出“规则/验收场景 → 代码与测试证据 → 通过/失败/未验证”。发现偏差时修复实现或显式提出需求变更，不能倒改规格使现有代码自动通过。验证不要求重写整份 Spec；发现真正的概念缺口才回退探索。
