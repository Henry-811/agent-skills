## 一、Design Principles (设计原则)

### SOLID

| 原则 | 含义 | 执行要求 |
|------|------|----------|
| **S** — Single Responsibility | 模块围绕一致的职责和变更原因组织 | 结合业务不变量、生命周期、责任主体和变更模式判断内聚，不按函数数或概念名称机械拆分。经常一起修改只是线索，也可能是错误耦合或共同编排造成；不能据此直接判定同一域。独立规则和测试矩阵见下文“复杂业务中的规则子域”。 |
| **O** — Open/Closed | 对扩展开放，对修改关闭 | **SHOULD** 当某类变化已重复出现或明确存在多实现并存需求时，通过注册/策略/插件等方式扩展，避免反复修改核心分发逻辑。不要为假设性扩展点提前设计插件体系。 |
| **L** — Liskov Substitution | 子类/实现可无缝替换 | **MUST** 所有实现必须完整遵守接口契约。 |
| **I** — Interface Segregation | 接口按需拆分 | **SHOULD** 不强迫依赖方依赖不需要的方法。多个小接口优于一个大接口。 |
| **D** — Dependency Inversion | 依赖抽象而非具体 | **SHOULD** 上层依赖接口/协议，不依赖具体实现。外部依赖通过注入传入，使用框架 DI 机制。 |

### DRY — Don't Repeat Yourself

- **MUST** 同一知识/逻辑只在一处表达。写新代码前，先查找项目中已有的同类实现，复用其模式。
- **SHOULD** 重复 3 次以上通常应提取为共享抽象。少于 3 次时，如果逻辑复杂、变更频繁、语义明确且抽象后更清晰，也可以提取。"3 次"是经验阈值，不是硬门槛。
- **ANTI-PATTERN** 为了消除表面相似而抽象出语义模糊的万能函数。每处虽然"长得像"但语义微妙不同时，保留重复比硬抽象更安全。

### KISS / YAGNI

- **KISS**：用最简单的方案解决当前问题。KISS 约束拆分**方式**（用最简方案拆），不否决拆分**决策**（SRP 判定该拆时必须拆）。
- **YAGNI**：不为假设的未来需求写代码。不加 feature flag、兼容层、预留扩展点，除非当前确实需要。
- **Make it work → Make it right → Make it fast**。

## 二、Clean Architecture (整洁架构)

### 分层结构

```
接口适配层（API / 页面） → 应用服务层 → 核心领域
基础设施适配器（数据库 / 外部服务） → 核心定义的接口
启动入口负责装配具体实现
```

### 依赖规则

- **MUST** 区分源码依赖与运行时调用：Service 可运行时调用 Repository，但抽象接口由需要它的业务层定义，数据库适配器实现接口。源码依赖保持无环，核心不反向导入框架、数据库、UI；项目已有合理分层可沿用，不为套图批量重构。
- **SHOULD** **默认不跳层**：Service 通过 Repository 访问数据，前端通过 API Client 请求后端。若场景极简单、生命周期短、无复用预期，可允许受控例外，但必须保证边界清晰，且后续能平滑演进到标准分层。
- **SHOULD** 对具有独立持久化职责或明确数据访问边界的实体，提供对应的数据访问模块。值对象、投影模型、外部 DTO 等不强制单独建立。

### 跨层数据转换

- **SHOULD** 默认区分 API、领域、存储模型。若边界稳定、语义一致、复用不会引入层间污染，可在局部场景谨慎复用，但需说明为什么可以复用。
- **SHOULD** 层间转换应显式、类型安全：通过 mapper / converter 完成；避免 `asdict()` → dict → `.get()` 这类松散传递。**注意**：域内的方法间暂存（如解析中间态、执行上下文传递）不属于层间转换，不受此条约束。判断标准是数据是否跨越了架构层边界，而非是否使用了 dict。
- **SHOULD** 业务层不应依赖存储模型的特有概念（如 ORM session、lazy loading）。若直接复用存储模型作为领域模型，确保不泄漏存储细节到上层。

### 模块组织：域优先，共享下沉

- **MUST** 业务逻辑归属明确的域。新功能属于既有域时在该域扩展，确有独立规则和生命周期时才新建域；router / service / schemas / repository 是常见形态，不是固定目录模板。通过清晰接口协作，不把“每个 feature 一个域”当成目标。
- **MUST** 共享基础设施按层组织：无业务规则的跨域模块（数据库、缓存、认证中间件、工具函数）放共享层（core/、db/）。**ANTI-PATTERN**：仅因"可能以后复用"就提前放入共享层。尚未形成稳定跨域复用前，优先留在所属域内。
- **SHOULD** 共享域服务独立成包：被多个域调用、但拥有自己业务规则的模块，独立为域包，不塞进调用方、也不降级为基础设施。
- 判断标准：
  - 只被一个域使用 → 放该域包内
  - 被多个域使用 + 有自己的业务规则 → 独立域包
  - 被多个域使用 + 无业务规则（纯工具/基础设施） → 共享层（core/、db/）
  - **ANTI-PATTERN**：把有业务规则的共享服务塞进某个调用方的域包。读代码的人会误以为该服务只服务于该域。

### 入口脚本 vs 业务逻辑

**SHOULD** 入口脚本（main.py 等）应尽量只保留装配和启动逻辑。即使当前没有第二个 import，如果代码已包含可测试、可复用、可独立理解的业务流程，也应提取。

### 增量式开发

- 先基础后功能，确保底层稳定后再往上搭。
- 模块间通过清晰的接口通信，不直接耦合实现。

## 执行细则（实战踩坑总结）

### 拆分判断：按域，不按行数

- 1500 行但只因一个域的需求变更 → 不拆
- 300 行但混了 3 个不相关域的逻辑 → 该拆
- 即使当前只被一处调用，如果代码包含可测试、可复用、可独立理解的业务流程，也值得提取
- 内聚 = 属于同一个域，不是"名字看起来相关"

### 复杂业务中的规则子域

在复杂业务中，一个大业务域内部可以包含多个规则子域。规则子域的判断依据是不变量、独立测试矩阵、状态生命周期和变更原因，而不是流程位置或名词名称。

仅消费其他子域结果做流程编排或策略选择的逻辑（application policy / orchestration）不是子域。它应留在编排层；强行拆出来会制造伪 domain 和不必要的间接层。

候选规则子域的判定信号（满足 2 条以上才考虑提取）：
- 有自己的不变量，违反后会导致数据或状态不一致。
- 有独立测试矩阵，输入维度与其他子域不重叠。
- 有自己的状态生命周期或派生规则。
- 修改它时不需要理解另一套子域的规则。

不是子域的伪信号：
- 在同一个用户流程里连续发生，只说明流程相邻，不说明规则相邻。
- 名字听起来是一个概念，只是命名分类，不是不变量分类。

候选子域不必立刻拆。规则量小、变更频率低时可以留在所属域内；当测试用例开始按子规则成簇、改一个子规则反复触发另一个子规则回归、或文件中出现大量"这一段只跟 X 有关"的注释墙时，再提取。

### KISS 约束拆分方式，不否决拆分决策

SRP 决定**是否拆**，KISS 决定**怎么拆**。SRP 判定该拆时，KISS 不能作为"不拆"的理由。

### Design Plan / ADR-lite 输出

中等及以上结构变更必须产出轻量 Design Plan。适用场景：新模块、跨层调用、Repository / Service 调整、领域拆分、共享模块、入口脚本承载业务流程、依赖方向变化。

1. **变更目标**：要解决的结构问题；不解决会造成什么风险。
2. **影响域**：涉及哪些业务域、基础设施层、接口层；哪些域不应被影响。
3. **放置位置**：新代码放在哪个域/层；为什么不是共享层或调用方内部。
4. **依赖方向**：调用关系、数据访问路径、是否跳层；若有例外，说明边界和演进路径。
5. **模型边界**：API / domain / storage model 是否复用；需要哪些 mapper / converter。
6. **替代方案**：存在实质选择时记录取舍；沿用明确的既有契约时说明依据，不编造候选方案凑表。
7. **验证方式**：用哪些测试、静态检查、手动验证或代码搜索确认边界没有破坏。

**门槛检查**：如果说不清新逻辑属于哪个域、依赖方向如何保持单向、或为什么当前拆分是最小必要拆分，不进入实现；先收敛 Design Plan。
