本 skill 用于把模糊想法推进到可执行需求。目标不是产出代码方案，而是先确认"做什么、为什么做、为谁做、做到什么程度"。

## 边界与产物

- **本 skill 产出 Concept Brief**——定义"问题是什么、谁有这个问题、做到什么算完成"。
- **本 skill 只用代表性场景界定概念和范围**；完整业务规则、流程覆盖与边界枚举由 product-check 负责。
- **Concept Brief 是 product-check 的输入**。Brief 未闭环时不进入 product-check 或代码实现。
- 触发时机：新产品、新业务域、用户可感知的新 feature 默认调用，不需要用户说"方向模糊"。

## 使用原则

- **MUST** 先外显假设，再讨论实现。不要把用户没说清楚的内容默认为事实。
- **MUST** 会改变产品方向、权限、数据损失风险或外部承诺的歧义，列出选项与 trade-off；先从上下文和现有规格核实，仍无法判断才请求决策。范围内可逆的实现细节可沿用项目惯例，显式说明假设后继续，不反复请求已给出的授权。
- **MUST** 区分事实、假设、决策和待验证问题。
- **SHOULD** 只问会改变方向的关键问题；能通过现有上下文合理确认的，不打断用户。
- **MUST** 存在阻塞性概念缺口时不进入产品代码实现。可进行范围明确、可丢弃的调研/技术 spike 获取证据，但不得把探索结果当作已获确认的产品方向。

## 执行流程

### 1. 问题框定

- 用户真正想解决的问题是什么？
- 谁有这个问题？是最终用户、运营者、管理员、开发者，还是其他角色？
- 这个问题现在为什么值得解决？不解决的代价是什么？
- 当前诉求是探索方向、定义 MVP、评审方案，还是准备实现？

### 2. 概念与术语

- 列出核心概念，并给出一句话定义。
- 标出容易混淆的概念、同义词和边界。
- 确认文档、UI、API、代码命名是否应使用同一套术语。
- 对每个关键概念说明：它是什么、不是什么、由谁创建、如何变化、何时结束。

### 3. 假设与未知项

把不确定性分成三类：

| 类型 | 处理方式 |
|------|----------|
| 必须先确认 | 不确认会改变产品方向、核心流程或数据模型 |
| 可以带假设推进 | 不影响近期实现，但需要在文档中标明 |
| 可以推迟 | 不影响 MVP 或当前决策 |

每条假设应说明验证方式：用户确认、数据验证、原型测试、业务规则推导或技术 spike。

### 4. 用户与场景

- 用具体场景描述触发条件、用户动机、输入、操作和期望结果。
- 至少覆盖主流程、替代流程和失败/退出路径。
- 判断是否存在多个用户角色，以及角色之间的权限、责任和信息差。
- 明确用户完成任务后的可见结果，而不只描述系统内部动作。

### 5. 范围与非目标

- 定义 MVP：最小闭环是什么？
- 明确暂不做什么，避免把探索问题直接扩成大而全方案。
- 说明哪些需求是后续增强，而不是当前验收标准。
- 若有多个方向，按价值、风险、实现成本和验证速度排序。

### 6. 可执行需求门槛

进入 product-check 或实现前，至少满足：

- [ ] 目标用户和核心问题明确。
- [ ] 核心概念有统一定义。
- [ ] 主流程从触发到结果闭环。
- [ ] 已识别会影响概念定义或 MVP 边界的关键约束（完整业务规则交由 product-check 校验）。
- [ ] 必须先确认的未知项已经解决；若仍有阻塞项，门槛未通过，只输出缺口和澄清路径。
- [ ] MVP、非目标和验收标准清楚。

## 输出格式：Concept Brief

产出或更新 Concept Brief；已有等价需求可直接引用，只补缺口。简单 feature 用简短条目覆盖以下信息，不要求新建同名文件：

1. **当前阶段判断**：概念探索 / 需求验证 / 方案设计 / 实现
2. **目标用户**：具体角色（最终用户 / 运营 / 管理员 / 开发者等）；多角色时列出各自的权限和信息差
3. **核心问题**：用户要完成的任务，以及不解决的代价
4. **核心概念定义**：每个新概念的"是什么 / 不是什么 / 由谁创建 / 如何变化 / 何时结束"
5. **MVP 边界**：最小可行闭环、验收标准
6. **非目标**：明确不做什么、推迟到后续的增强
7. **关键假设**：事实 / 假设（含验证方式）/ 待验证问题
8. **待确认问题**：阻塞性问题，需要用户决策才能动手（含多解读时的方向选项与 trade-off）

**门槛检查**：目标、核心概念、MVP 或必须先确认的问题未解决时，**不进入 product-check 或产品代码实现**。没有假设/待确认问题可明确写“无”；不适用项写 `N/A + 理由`，不为凑格式制造阻塞。

## 与其他 skill 的关系

- 概念、术语、目标用户或成功标准不清楚时，先用本 skill。
- 需求已经成形、需要检查业务规则和流程完整性时，再用 product-check。
- 准备写代码、重构或审查时，再用 dev-principles。
