# Testing Methodology (测试方法论)

### 1. 测试金字塔

| 层级 | 定位 | 测什么 | 特点 |
|------|------|--------|------|
| **单元测试** | 主体 | 单个函数/方法的逻辑正确性 | 快、隔离、无外部依赖 |
| **集成测试** | 验证协作 | 模块间协作、数据库交互、API 端点 | 真实依赖，验证层间契约 |
| **E2E 测试** | 关键路径 | 完整用户流程 | 慢，只覆盖核心业务路径 |

- **SHOULD** 以单元测试为主，集成测试验证协作，E2E 只覆盖关键路径。具体比例可随系统形态调整（纯算法库单元测试占比更高，强集成系统集成测试占比更高），不作为硬性考核指标。
- **SHOULD** 用最低成本且能真实暴露缺陷的层级复现 bug。单元测试能复现局部逻辑，不代表已验证 provider、数据库语义、跨层契约或 UI；涉及这些风险时补相应集成或浏览器测试。

#### E2E 测试基础设施

- **MAY** 前端 E2E：Playwright。后端/数据库：docker-compose 拉起完整测试环境。
- **SHOULD** 环境隔离：独立 `docker-compose.test.yml`，测试数据库每次运行前重置。

#### E2E vs 后端测试：选择标准

**原则：后端测试验证服务与数据行为，组件/浏览器测试验证用户交互与呈现，E2E 验证关键链路。不要在高成本层重复穷举已有边界用例，也不能用后端通过代替前端验证。**

| 用 E2E（Playwright） | 用后端集成测试 |
|---|---|
| **前后端联通**：后端新增/修改功能后，前端是否正确调用 API 并渲染结果 | 单个 API 端点的输入/输出/状态码/边界值 |
| **跨页面流程**：用户从 A 页面操作后到 B 页面看结果 | 业务规则验证（权限、级联、并发） |
| **前端状态联动**：操作后 UI 自动更新（轮询、WebSocket、状态流转） | 参数校验（422）、空值/边界 |
| **浏览器特有行为**：文件上传 UI、下载触发、语音识别、快捷键 | Mock 模式下的异步任务触发 |

**何时必须写 E2E：**
- **SHOULD** 新增功能涉及前后端联动时（后端加了接口 + 前端要展示），有 E2E 验证数据从 API → 页面的完整链路。
- **SHOULD** 关键业务流程（注册→使用→产出结果）有端到端覆盖。

**E2E 不测什么：**
- 不测单个 API 的边界值（后端测试覆盖）。
- 不测纯后端逻辑（service 层、竞态、鉴权规则）。
- 不按页面数量机械铺 E2E。单页也是合法用户流程；列表渲染、空态、错误态可由组件或浏览器测试验证，后端测试不能证明页面正确。

### 2. 场景覆盖清单

**SHOULD** 每个功能覆盖以下 7 类场景（视复杂度裁剪）：

| # | 场景类型 | 说明 |
|---|----------|------|
| 1 | **Happy Path** | 正常输入，预期输出 |
| 2 | **Error Path** | 业务规则违反、外部服务失败 |
| 3 | **Boundary** | 边界值、极端值 |
| 4 | **Empty / Null** | 空值、缺失字段、空集合 |
| 5 | **Auth & Permission** | 未登录、角色越权、资源归属 |
| 6 | **Idempotency & Concurrency** | 重复提交、并发操作 |
| 7 | **Data Integrity** | 关联数据一致性、级联操作 |

写测试前先列出每类场景的具体用例，再逐一实现。

#### Test Plan 输出

中等及以上变更、bugfix、业务规则变化，或已由 product-check 产出 Feature Spec 时，实现前明确 Test Plan，并在实现中更新证据。小 bugfix 可用复现条件、回归断言和命令三项表达，不要求补造 Feature Spec：

| 字段 | 要求 |
|---|---|
| 场景来源 | Feature Spec 的业务规则/验收场景，或已确认的 bug 复现、现有契约 |
| 风险类型 | happy path / error / boundary / empty-null / permission / concurrency / data integrity |
| 测试层级 | unit / integration / E2E / manual verification |
| 覆盖方式 | 说明具体测什么、断言什么、使用真实路径还是 mock/fake |
| 不测理由 | 对不自动化覆盖的场景说明原因、风险和替代验证方式 |

- **MUST** 每条关键业务规则和验收场景至少映射到一个验证方式。
- **MUST** bugfix 至少有一个回归验证方式；无法自动化时说明阻塞原因和手动复现步骤。
- **MUST** 用 fake / mock / local fallback 替代受影响的集成行为时执行 R5：在隔离环境覆盖 production default provider / backend / branch / SQL path。纯算法/映射单测可隔离无关依赖；无法运行真实路径时报告未验证项，不把 mock 通过当成完成证据。
- **MUST** 命中 R9 时，Test Plan 标出由哪个测试执行真实 production coordinator/effect、如何 flush 异步工作并等待状态收敛，以及哪些外部边界被 mock。不会执行 effect 的伪 Hook 测试只能覆盖纯渲染或派生逻辑，不能登记为异步编排覆盖。
- **MUST** 命中 R8 时，Test Plan 必须与证据支持的演进策略一致：无影响直接删除时记录发布/消费者/经授权的生产使用证据来源、部署和回滚事实，不记录敏感数据本身；维护窗口切换时覆盖 preflight、切换后验证及声明的恢复路径；兼容发布时覆盖真实部署矩阵和 contract 退出条件；证据未知时不能把方案标记为已验证。旧实现测试本身不能成为保留兼容层的理由；删除断言旧行为仍可用的测试，保留断言旧输入被拒绝/剥离、旧响应字段不再暴露、历史数据只由 migration 消费、downgrade/restore 正确以及审计/安全边界的测试。
- **SHOULD** 不把所有场景都塞进 E2E。优先用最低成本、能真实覆盖风险的测试层级。

### 3. 测试编写规范

- **SHOULD** **命名**：`test_should_<expectedBehavior>_when_<condition>`
- **SHOULD** **结构**：Arrange → Act → Assert (3A)
- **SHOULD** 单元测试尽量一测一行为；集成测试、E2E 可围绕一个业务流程断言多个关键结果，但应避免无关断言堆积。
- **MUST** **隔离**：测试间无共享状态、无执行顺序依赖。
- **SHOULD** **Mock 策略**：默认使用真实业务对象。单元测试可隔离外部 API、时钟及无关协作者；验证数据库、文件系统或外部协议时，按风险使用隔离数据库、临时目录、沙箱服务或契约测试。禁止未经授权向生产发送测试写入/邮件。Mock 不能替代被测行为；交互参数属于业务契约时必须断言，不验证无关内部细节。
- **SHOULD** **调用链测试**：当 bug 根因在函数之间的衔接上（类型转换、调用顺序、层间数据传递），必须补一类能覆盖真实调用链的测试——可以是 pipeline test、集成测试或更高层测试，关键是使用真实对象与真实转换验证链路，仅断言对识别调用链缺陷有价值的关键中间状态，避免把测试绑定到无关实现细节。

#### 前端异步 coordinator / effect

- **MUST** 行为由 `useEffect` / `useLayoutEffect`、异步 coordinator、subscription、polling、timer、请求取消或服务端状态同步驱动时，至少一条测试挂载并执行真实生产 Hook/coordinator/effect，在框架认可的 `act` / flush 机制内等待可观察状态收敛。
- **MUST** 保留被测编排层为真实实现。网络、时钟、浏览器 API 等外部边界可以 mock/fake；不得把 production effect、coordinator 或状态归并逻辑替换成预设返回值后声称覆盖了异步流程。
- **MUST** 覆盖当前风险相关的触发、异步副作用和最终状态；存在 cleanup、取消、过期响应、重复订阅或竞态风险时，至少覆盖对应的退出/恢复路径。
- **SHOULD** 纯 reducer、selector、mapper 和派生函数继续用快速单元测试覆盖，但它们只能补充真实编排测试，不能替代后者。
- **ANTI-PATTERN**：测试 harness 把 `useEffect` 实现为 no-op，随后只断言初始 render 或手工调用内部 callback，却把结果标记为 Hook 异步逻辑已验证。

### 4. 测试数据管理

- **SHOULD** **Factory 优先**：用 factory/builder 生成测试数据，不在每个测试里硬编码大段对象。
- **SHOULD** **默认合法，差异覆盖**：factory 返回合法默认值，测试只覆盖当前场景需要的字段。
- **MUST** **禁止共享可变 fixture**：每个测试拿到独立的数据实例，不在测试间共享可变对象。
- **SHOULD** **时间可控**：依赖当前时间的逻辑通过可替换的时间源访问，而不是直接散落调用系统时间；测试中应固定时间源，避免 flaky。
- **MAY** **参数化测试**：边界值、空值、多种输入格式优先用 `@pytest.mark.parametrize`，减少重复 setup。行为差异明显时拆开写。

### 5. 测试可维护性

- **SHOULD** **断言业务意图，不绑定实现细节**：断言"返回值是什么"、"状态变成什么"，避免断言内部私有方法调用次数、精确 SQL 文本等脆弱细节。
- **SHOULD** 重复 setup 超过 2 次就抽 helper/factory，但 helper 不要过度抽象到难以理解。
- **SHOULD** 测试也是代码：同样遵守命名、DRY、可读性要求。但测试中允许适度的显式重复以保持可读——宁可每个测试多写两行，也不要让 helper 嵌套三层。

### 6. 何时写测试

| 场景 | 强度 | 策略 |
|------|------|------|
| 新功能 | SHOULD | 应尽快补齐测试。若采用先实现后补测试的节奏，应在同一开发闭环内完成，不得把测试留到后续模糊时间点 |
| Bug 修复 | SHOULD | 优先先写失败测试复现；若因竞态、环境、时序等原因无法先稳定复现，先最小化修复，再尽快补足回归测试 |
| 重构 | MUST | 先确保有充分测试覆盖，测试全绿才算完成。不得降低已有测试保护面 |
| API 端点 | SHOULD | 覆盖本接口实际约定的成功、校验失败、未认证/越权、不存在与冲突语义；不强套固定框架的状态码清单 |
| 前端异步 coordinator / effect | MUST | 至少一条测试执行真实生产编排并等待状态收敛；外部边界可 mock |
| 高并发/权限/外部集成 | MAY | 按风险补充性能、安全、恢复性专项测试；关键业务或数据风险可提升为 MUST |

### 7. Flaky Test 治理

- **MUST** Flaky test 视为缺陷，不是"偶发可接受现象"。
- **SHOULD** 测试失败必须区分：代码问题 / 环境问题 / flaky。
- 常见 flaky 来源：依赖真实时间、sleep、共享数据库状态、外部网络、执行顺序。
- **SHOULD** 发现 flaky 后：立即标记并纳入修复队列。必要时临时 skip，但必须注明原因与影响范围。
- **MUST** 禁止通过删除断言、弱化断言、添加 retry 使测试"变绿"。

### 8. 测试文件组织

- **SHOULD** 测试目录可按层或按域组织，默认以"最容易定位被测对象"为准。若生产代码强烈按域组织，测试也可优先镜像域结构。
- **SHOULD** 测试文件与被测模块一一对应：`test_<模块>.py` / `<模块>.test.ts`
- **SHOULD** Fixtures / helpers / factories 集中管理（`conftest.py` / `tests/helpers/`）
